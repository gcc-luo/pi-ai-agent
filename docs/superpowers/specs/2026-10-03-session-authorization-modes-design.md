# 会话级授权模式设计

## 背景与目标

调用插件、连接器、浏览器和桌面操作时，当前常以单次确认弹窗放行。Pi 的 Bash 和本地文件工具不经过相同的授权入口。用户希望在对话输入框左侧提供 Codex 风格的授权模式菜单，并让设置覆盖会话中的所有 Pi 工具调用。

目标是统一授权体验，并在执行边界实施所选策略：

- **请求批准**：每次 Pi 工具调用执行前都请求用户批准。
- **帮我批准**：保留当前按风险决定是否弹确认的行为，为新会话默认值。
- **完全访问**：跳过 Pi 工具调用的确认弹窗。

模式按会话持久化，不同会话可使用不同模式。切换模式只影响后续调用，不改变已经显示的确认请求。

## 交互设计

在对话输入框左侧显示当前授权模式；点击后展开三个选项及简短说明。菜单遵循视觉伴侣原型，选中“完全访问”时以醒目强调色表示。选择后立即保存到当前会话，不增加二次确认弹窗。

重连或从其他窗口打开会话时恢复已保存的模式。旧会话和新会话的初始模式均为“帮我批准”，从而延续现有风险确认体验。

## 授权策略与执行范围

每个授权决策读取当前会话模式，并统一处理 Pi 核心工具以及插件、连接器、浏览器和桌面操作。核心 Bash、read、write、edit 工具必须在 Pi 执行前被拦截。宿主集成继续使用其现有权限入口，但调用共同的会话授权策略，并保证同一工具调用最多触发一次确认。

决策规则如下：

| 模式 | 普通工具调用 | 当前风险调用 | 显式拒绝或已禁用能力 |
| --- | --- | --- | --- |
| 请求批准 | 请求批准 | 请求批准 | 拒绝 |
| 帮我批准 | 按当前策略放行 | 请求批准 | 拒绝 |
| 完全访问 | 放行 | 放行 | 拒绝 |

“完全访问”只跳过应用内工具调用的确认，不会启用已禁用插件、覆盖连接器的明确拒绝策略，或更改应用与操作系统本身的权限设置。普通用户界面操作（如删除会话、卸载插件）不属于 Pi 工具调用授权模式。

## 状态与数据流

1. 前端显示会话 DTO 中的授权模式；新会话从默认值“帮我批准”开始。
2. 用户在输入框左侧菜单更改模式。服务端验证模式值并持久化到会话记录，再通过会话更新事件同步已连接客户端。
3. 工具执行前，Pi 核心工具钩子或宿主集成的权限入口把会话、工具、动作与参数摘要交给共同的授权策略。
4. 策略按当前模式及集成自身的启用/拒绝规则决定放行、拒绝或发出权限请求。
5. 需要批准时沿用现有 WebSocket 权限请求/响应机制；批准后只继续当前工具调用，不授予长期工具例外。

会话授权模式需要加入数据库迁移和共享 DTO/API。有效枚举值为 `approve_each`、`risk_based`、`full_access`，缺失或无效值按 `risk_based` 处理。权限策略在数据库或运行状态不可用时失败关闭：需要批准的操作不得在未经批准时继续。

## 失败处理与兼容性

- 确认被拒绝、超时、会话结束或 WebSocket 断开时，当前操作不执行或按现有取消语义终止。
- 切换模式时不回溯更改已经发出的待处理确认。
- 旧数据库通过迁移补齐字段，既有会话保持当前风险确认行为。
- 未知模式、读取失败或服务端授权状态无法确认时，不得因此自动授予权限。
- 对同一调用在核心钩子和宿主集成间建立单次授权上下文，避免重复弹窗。

## 验收与测试范围

- 新会话和旧数据库迁移后的会话默认 `risk_based`；三种模式在更新、重连及多客户端订阅后正确持久化与同步。
- `approve_each` 在核心工具和宿主集成每次调用前请求批准。
- `risk_based` 保留现有低风险放行和高风险确认行为。
- `full_access` 可无弹窗调用 Bash、read、write、edit、插件、连接器、浏览器及桌面能力。
- 显式禁用和拒绝策略在三种模式下均拒绝；授权超时或授权服务不可用时不误放行。
- 同一工具调用最多显示一个确认弹窗。
- 输入框左侧选择器可访问、正确展示当前模式，并可在会话间切换而不串值。

## 范围外

- 对文件、网络或进程的细粒度规则编辑器。
- 更改连接器的独立策略配置、插件启停状态或系统级沙箱设置。
- 对非 Pi 工具调用的普通管理操作增加授权模式门控。
