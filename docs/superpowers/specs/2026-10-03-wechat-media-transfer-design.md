# 微信会话图片与文件收发设计

## 背景

当前微信 Worker 从 `IncomingMessage` 只取 `userId` 和 `text`，没有把 SDK 提供的图片、文件媒体项交给 Agent。虽然 `RpcBridge` 已支持把图片附件转成 Pi RPC 所需的 `ImageContent`，微信服务没有使用这条链路。

当前已有的出站能力是 Agent 声明本轮生成的 `<artifacts>`，后端校验项目工作目录内的路径后读取文件，再由 `@wechatbot/wechatbot` 发送。参考项目另外支持接收入站图片和文件、合并短时间内到达的文本与附件，以及由 Agent 按需发送本地文件。

两个项目使用的微信 SDK 和 Agent 运行边界不同。本项目的 Agent 在单独子进程内运行，因此复用能力设计和当前 SDK，不移植参考项目的 iLink 加密与 CDN 协议实现。已有 `WeChatBot` 提供 `downloadRaw()`、`reply()` 和 `send()` 媒体接口；其中 `download()` 只选择一项媒体，处理多附件时应按消息中的媒体项逐个调用下载接口。

## 目标

1. 微信用户可以发送多张图片给 Agent；图片作为多模态输入进入 Pi 会话，并能在 Web UI 会话历史中查看。
2. 微信用户可以发送文件；后端将文件安全地保存到绑定项目的 `wechat-files/` 目录，并将文件名和相对路径交给 Agent。
3. 微信会话可以把项目中的已有普通文件按需发送给当前微信用户。
4. 保留 Agent 新生成文件的自动回传，并让图片文件继续通过 SDK 的扩展名路由按图片发送。
5. 把同一用户短时间内连续发送的文本和附件合并为一个 Agent turn，保持每个用户会话的串行执行。
6. 对附件数量、体积、模型图片能力、路径边界及发送错误给出明确处理。

## 非目标

- 不支持视频、语音转写或群聊附件。
- 不允许按需发送项目工作目录以外的文件，也不支持目录递归发送或自动打包。
- 不复制参考仓库的微信加解密、CDN 上传或 iLink 请求协议。
- 不新增前端附件上传器；微信附件由微信消息进入系统。
- 不实现参考仓库基于文本语义的 20 秒附件关联规则。

## 方案选择

### 方案 A：复用当前 SDK 和 RPC 图片链路（采用）

Worker 使用 SDK 的消息媒体对象和下载接口处理全部附件。图片映射成当前共享类型的 `ImageAttachment`，通过已有 `RpcBridge` 的 `images` 字段交给 Pi；文件保存到项目工作目录并作为相对路径提示 Agent。出站继续调用 SDK 的媒体发送接口。

按需发送工具作为仅微信 Agent 进程加载的扩展。扩展通过带短期令牌的内部 HTTP 接口把文件路径交给后端；后端确认当前会话和项目范围，再调用 Worker 当前消息的发送回调。微信凭证、用户 ID 和消息上下文令牌只保留在服务端内存中，不写入 Agent prompt 或项目文件。

优点：沿用项目已有的图片 RPC 和 SDK 媒体实现；保留 SDK 对微信媒体加密、上传、下载的维护；工具路径校验和发送逻辑留在主服务进程。代价：需要为仅微信 Agent turn 增加扩展启动参数和受令牌保护的内部接口。

### 方案 B：移植参考仓库的媒体协议实现

在本项目中重写媒体下载、解密、上传和发送协议。

不采用。当前 SDK 已提供对应接口；重复实现会产生两套协议边界和错误处理，也会扩大凭证与协议代码的维护范围。

### 方案 C：仅通过 `<artifacts>` 声明按需文件

要求 Agent 将已有文件作为最终产物声明，复用现有自动回传流程。

不采用。该协议表达的是最终产物，不能为 Agent 提供清晰、可观察的“发送文件”操作结果，也不符合已确认的按需发送工具需求。

## 数据流

### 入站消息与附件聚合

```text
WeChatBot IncomingMessage
  → 按 userId 接入串行队列与短窗口聚合
  → 按媒体项下载并解密所有图片和文件
  → 图片转 ImageAttachment；文件安全写入项目目录
  → 持久化用户文本及图片 metadata
  → RpcBridge.send({ content, images })
  → Agent 生成回复
```

- 纯文本消息的静默聚合窗口为 500ms；批次中出现图片或文件后，静默窗口延长至 3 秒，并在同一用户有新文本或附件到达时重新计时。
- 聚合范围只包含相同微信用户的消息；不同用户仍并行处理。合并结果保留消息时间顺序，图片和文件也按原顺序保留。
- 入站最多处理 4 张图片和 10 个文件。图片允许 PNG、JPEG、GIF、WebP，单张不超过 5 MiB，图片总量不超过 20 MiB。文件单个不超过 50 MiB、总量不超过 100 MiB。
- 文件保留原始显示名；落盘名增加时间戳和随机标识，并清理路径分隔符及控制字符。文件只写入绑定项目根目录下的 `wechat-files/`，相对路径必须保持在根目录内。
- 文件附件以“文件名、相对路径”加入 Agent 可见的用户输入，并以 metadata 保存在用户消息中；不把文件正文写入 prompt。
- 图片保存为用户消息 metadata 中与 Web UI 既有图片消息一致的 `{ name, mediaType, data }` 结构，并随 `RpcBridge` 的 `images` 字段进入 Pi 会话 transcript。
- 如果本轮包含图片而所选模型不是 `multimodal`，本轮不启动 Agent，向微信用户返回切换到多模态模型的提示。
- 超出数量或大小上限、媒体下载/解密失败、文件名无效、项目目录不可用时，返回简洁中文错误，不把凭证、绝对工作目录或异常堆栈发送给微信用户。

### 出站文件和图片

```text
Agent 生成的 artifacts ─→ 现有路径校验与大小限制 ─┐
                                                  ├→ WeChatBot.reply({ file, fileName })
send_file_to_wechat tool ─→ 受保护的内部接口 ────┘
```

- 保留现有 `<artifacts>` 声明和项目内路径校验、符号链接逃逸保护、单文件 50 MiB 与总量 100 MiB 限制。
- 新增 `send_file_to_wechat({ filePaths: string[] })`，只接受相对于当前项目工作目录的普通文件路径；单次最多 10 个文件、总量最多 100 MiB，按给定顺序逐个发送。
- 发送工具在 Agent 子进程中不直接访问微信凭证。扩展把路径提交到仅当前 WeChat session 可调用的内部接口；服务端使用本轮内存中的发送回调通过当前 SDK 消息上下文发送文件。
- Agent 工具结果逐个报告成功或失败；一个文件发送失败不阻止剩余文件。Agent 可据结果向用户总结。
- 生成或选择的 PNG、JPEG 等图片仍作为文件产物进入 SDK；SDK 根据文件名扩展名选择图片发送形式。
- 工具不在桌面端普通 Agent 会话加载。即使伪造内部请求，缺少当前进程的短期令牌或有效会话上下文也必须被拒绝。

## 组件职责

- `wechat-worker`：归一化 SDK 入站消息，维护用户级队列和聚合窗口，负责下载媒体及通过原消息上下文发送回复。
- `wechat-media`（新增）：检查媒体类型、数量和大小，安全命名和保存入站文件，构造 Agent 可消费的图片与文件元数据。
- `wechat-agent-service`：接受富媒体输入，检查当前模型图片能力，持久化用户消息，构造包含文件相对路径的 prompt，并向 `RpcBridge` 传图片。
- `process-manager`：只对微信 Agent turn 加载文件发送扩展，并为该 session 签发短期令牌。
- `wechat-file-transfer` 内部路由：验证短期令牌、WeChat session 活跃状态和路径范围，再调用当前 Worker 的发送回调。
- `wechat-artifacts`：继续负责 Agent 最终产物的解析、安全路径验证和加载。
- Web UI：复用已有的用户图片 metadata 渲染；文件名和相对路径通过用户消息文本保持可见，不新增附件组件。

## 错误处理与生命周期

- 同一用户的完整聚合、Agent turn、工具文件发送和产物回传按序执行；不同用户互不阻塞。
- 用户在附件聚合窗口内发来的内容按消息时间排序并合并。停止 Worker 或退出登录时清空定时器、聚合缓存和待处理队列。
- 媒体校验在下载前能根据消息元数据拒绝的附件，应在下载前拒绝；下载后再次检查实际字节数及图片文件签名，防止依赖不可信的声明大小和扩展名。
- 文件保存采用不会覆盖已有文件的创建方式。符号链接和解析后落到项目根目录外的路径一律拒绝。
- 内部发送接口令牌只允许用于一个 session；Agent 子进程结束后撤销。接口只接受相对路径，不接受 Agent 提供的收件人、context token 或任意 URL。
- 工具或 artifact 发送失败时记录安全摘要并回传文件名级别的错误，不记录文件正文或凭证。

## 验收标准

1. 单个微信消息中的 1–4 张图片能作为图片输入被多模态模型分析，且在 Web UI 历史中显示。
2. 第 5 张图片、超出体积的图片、无法识别的图片格式和 text-only 模型均得到明确提示，不产生无效 Agent turn。
3. 多条连续文本/附件消息在 500ms/3s 窗口内按用户合并；不同用户不会合并或串行阻塞。
4. 支持的文件能写入项目 `wechat-files/`，Agent 输入包含安全相对路径，路径逃逸和重名覆盖被拒绝。
5. `send_file_to_wechat` 可按顺序发送项目内多个文件并给出逐文件结果；绝对路径、越出项目目录路径、目录和缺失文件均不发送。
6. 新生成的普通文件和图片产物继续自动回传；单文件失败不会阻止其余文件发送。
7. 普通桌面 Agent 会话无法使用微信发送工具；过期或无效短期令牌请求被拒绝。

## 验证策略

- 覆盖媒体下载、MIME 签名检查、限制值、文件落盘路径防护、消息聚合和队列隔离。
- 覆盖 `WechatAgentService` 的图片透传、消息历史 metadata、text-only 模型拒绝和文件路径 prompt。
- 覆盖微信文件发送扩展的令牌请求、目录/路径拒绝、顺序发送、单文件失败后的继续发送，以及 artifacts 回归。
- 验证目标包括 Server TypeScript 构建、微信相关自动化用例和一次真实账号端到端收发验收。
