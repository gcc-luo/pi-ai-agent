# 会话切换后用户消息重复修复设计

## 背景与根因

发送消息时，Web 前端会先在 `agent.streams` 中加入一条本地乐观消息；
重新进入会话时，`ChatPanel` 又会加载数据库中的持久化消息，并将两种来源合并。

当前用户消息只能通过“文本、图片名称、媒体类型、图片数据完全一致，且时间戳
相差不超过 10 秒”识别为同一条。图片请求进入 Pi 前可能经历较长处理，Pi 转录
同步又会用转录时间覆盖数据库时间。本次实例中，本地消息时间为 `09:07:16`，
持久化消息时间为 `09:07:37`，21 秒的差值超过去重窗口，因此同一条消息被显示
两次。数据库和 Pi 转录中实际只有一条用户消息。

## 目标

- 会话切换后，同一条本地消息和持久化消息只显示一次。
- 不依赖图片处理耗时或客户端、服务端时间差。
- 连续发送内容完全相同的消息时，不错误合并。
- 已有历史数据仍可正常显示和使用原有兜底去重。

## 方案

采用前端生成的稳定消息标识 `clientMessageId`：

1. `agent.send` 创建本地用户消息后，把该消息 ID 作为可选
   `clientMessageId` 随 WebSocket `send` 事件发送。
2. 服务端将 `clientMessageId` 写入用户消息 metadata，并保留现有图片与知识库
   metadata。
3. `ChatPanel` 构造合并数据源时，从持久化 metadata 读取
   `clientMessageId`；本地消息直接使用自身 ID。
4. `mergeChatMessageSources` 优先按稳定 ID 一对一合并，并保留现有的内容签名与
   时间窗口作为旧数据的兼容兜底。

字段是可选的，因此旧客户端、旧服务端和旧消息不会发生协议不兼容。

## 数据流

```text
用户发送
  -> Web 创建本地消息 u-...
  -> WebSocket send(clientMessageId=u-...)
  -> Server 持久化 metadata.clientMessageId
  -> 切回会话并加载历史
  -> persisted.clientMessageId 与 live.id 精确匹配
  -> 保留持久化消息，移除本地副本
```

## 错误与兼容处理

- 没有 `clientMessageId` 的历史消息继续使用内容签名和 10 秒窗口匹配。
- 服务端收到缺少 `clientMessageId` 的旧客户端事件时照常持久化。
- 重试沿用原本地消息 ID，避免同一次发送产生新的身份。
- `clientMessageId` 只用于展示层关联，不作为数据库主键，也不改变消息排序。

## 测试

遵循红—绿流程补充以下回归覆盖：

1. 持久化与本地用户消息时间相差超过 10 秒，但稳定 ID 相同，最终只保留
   持久化消息。
2. 内容完全相同但稳定 ID 不同的消息不会因稳定 ID 路径错误合并。
3. `agent.send` 与重试事件携带正确的 `clientMessageId`。
4. 服务端将 `clientMessageId` 与图片 metadata 一起持久化。
5. 运行 Web 单元测试、Server 相关测试、类型检查和构建。

## 非目标

- 不调整 Pi 转录时间戳的语义。
- 不修改消息排序、流式回复生命周期或图片上传格式。
- 不清理已有的本地 stream 缓存。
