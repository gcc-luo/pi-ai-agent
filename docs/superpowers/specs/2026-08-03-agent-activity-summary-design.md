# Agent 执行过程聚合展示设计

## 背景

当前对话界面会将 Pi 在一次用户请求中产生的每段 `thinking` 和每次
`tool_call` 逐条渲染。连续执行搜索、读取和 Bash 命令时，活动中的任务会
不断新增消息块并推动页面滚动，最终回答反而被大量过程信息淹没。

项目已有 `annotateChatRuns`，能够按用户消息划分一次完整的 Agent run，
但目前只在 run 完成后折叠中间消息。活跃 run 仍完整展示所有过程块，
因此没有解决执行期间的刷屏问题。

## 目标

- 一次用户请求只展示一个持续更新的活动摘要，不因工具数量增加而拉长页面。
- 最终回答保持独立、清晰，并且始终是默认视图的视觉重点。
- 完整思考与工具记录仍可查看，便于排错和建立用户信任。
- 运行中、完成后和刷新后的历史会话使用一致的展示规则。
- 不修改现有 WebSocket 协议、数据库结构和历史消息格式。

## 非目标

- 不改变模型调用工具的频率或 Agent 的执行策略。
- 不由前端解释或总结模型的详细思考内容。
- 首期不引入服务端阶段事件，也不迁移历史数据。
- 不隐藏权限确认、危险操作确认和需要用户响应的交互。

## 方案选择

### 采用：前端展示层聚合

保留原始 `MessagePart[]`，在 `chat-run-presentation.ts` 中将同一 run 的
思考和工具事件投影成一个活动视图模型。新组件负责摘要及详情展示。

该方案改动集中，兼容实时事件和历史数据，也能复用项目已有的 run 划分。
未来服务端可以补充更准确的阶段语义，而不必推翻前端组件。

### 未采用：服务端生成阶段事件

服务端可以把原始调用归纳为“分析、修改、验证”等阶段，语义更稳定，
但需要调整协议、持久化和历史恢复。当前问题主要是展示密度，首期成本过高。

### 未采用：仅隐藏现有过程块

用模板条件或 CSS 隐藏逐条记录实现最快，但无法可靠统计操作、表达当前状态，
也容易吞掉错误，不能形成可扩展的交互模型。

## 交互设计

### 运行中

每个活跃 run 只显示一行活动摘要，内容原地更新：

```text
◌ 正在分析项目 · 已完成 6 项操作 · 当前：搜索前端测试
```

- 摘要位于本次回复的顶部，不随新工具调用创建新消息块。
- 默认收起；用户可以随时展开查看时间顺序的完整过程。
- 展开后，新事件追加在详情内部，不改变用户主动选择的展开状态。
- 摘要更新本身不触发自动滚动，避免页面持续跳动。
- 思考内容不默认展示，也不在摘要中复述。

### 完成后

任务结束后，摘要变为静态结果：

```text
✓ 已处理 1m 14s · 9 项操作 · 查看详情
```

- 默认收起，完整记录仍可展开。
- 最终回答独立显示在摘要之后。
- 若存在失败，摘要显示失败数并使用错误色，例如
  `已处理 42s · 8 项操作 · 1 项失败`。
- 展开包含失败的摘要时，优先将第一个失败项滚动到可见位置。

### 必须突出显示的事件

以下内容不进入普通折叠流程：

- 权限确认或危险操作确认。
- 需要用户补充信息的请求。
- 阻止任务继续的顶层错误。

它们继续使用独立卡片或错误提示，确保用户能够发现并响应。

## 展示模型

`annotateChatRuns` 继续负责划分 run，并为每个 run 生成一个活动对象。建议的
前端内部类型如下；它不是共享协议的一部分：

```ts
interface AgentActivity {
  runId: string;
  status: "running" | "complete" | "failed" | "interrupted";
  startedAt: number | null;
  durationMs: number | null;
  currentLabel: string | null;
  operationCount: number;
  completedCount: number;
  failedCount: number;
  items: AgentActivityItem[];
}

interface AgentActivityItem {
  id: string;
  kind: "thinking" | "tool" | "raw";
  label: string;
  status: "running" | "complete" | "failed";
  part: MessagePart;
}
```

统计口径如下：

- `operationCount` 只统计工具调用，不将思考片段计入“操作”。
- `completedCount` 包含成功和失败的已结束工具调用。
- `failedCount` 复用现有 `toolResultFailed` 判定规则。
- `currentLabel` 优先取最后一个运行中的工具；没有运行中工具时取最近完成项。
- 同一 `toolCallId` 的 call、progress 和 result 合并为一个条目，不重复计数。

## 易读标签

活动摘要不直接展示冗长命令，而是根据工具名和参数生成短标签：

| 调用类型 | 摘要标签示例 |
| --- | --- |
| Bash 搜索、文件搜索、读取文件 | 搜索代码、检查项目、读取文件 |
| 写入、编辑、补丁 | 修改文件 |
| 测试、类型检查、构建 | 验证结果 |
| 浏览器相关工具 | 操作浏览器 |
| 其他或未知工具 | 执行操作 |

详情中仍展示现有工具名、参数、进度和结果。标签生成必须有安全回退，未知工具
不得导致渲染失败。首期使用确定性规则，不调用模型生成摘要。

## 组件边界

### `chat-run-presentation.ts`

- 划分 user turn 对应的 run。
- 从消息 parts 生成 `AgentActivity`。
- 决定哪些 assistant 文本属于最终可见内容。
- 提供纯函数，供实时消息和持久化消息共同使用。

### `AgentActivity.vue`

- 渲染运行态和完成态摘要。
- 管理本地展开状态及无障碍属性。
- 展开时复用现有的思考、工具参数、进度和结果展示能力。
- 只接收展示模型，不直接读取 store 或处理 WebSocket 事件。

### `ChatPanel.vue`

- 组合用户消息、活动组件、最终回答和产物卡片。
- 不再在顶层逐个渲染 `thinking`、`tool_call` 和 `raw` 过程块。
- 保留 run 耗时、停止任务和最终回答的现有行为。

为避免 `ChatPanel.vue` 继续变大，现有工具详情模板和样式随新组件迁移，
不在两个组件中复制。

## 数据流

```text
WebSocket / 历史 API
        ↓
原始 MessagePart[]
        ↓
按用户消息划分 run
        ↓
生成 AgentActivity + 最终可见内容
        ↓
AgentActivity.vue + 最终回答
```

实时事件仍由 agent store 合并进 `MessagePart[]`。展示层每次重算时通过
`toolCallId` 保持条目身份稳定，因此进度和结果只更新已有行，不新增重复行。
刷新后，`partsFromPersisted` 还原相同 parts，再生成相同活动模型。

## 滚动策略

- 用户位于消息区底部时，最终回答新增文本可以继续自动跟随。
- 用户主动向上滚动后，不因活动摘要、进度或耗时更新抢回滚动位置。
- 活动摘要高度不变时不触发滚动。
- 用户展开详情导致高度变化时保留当前视口，不自动跳到底部。
- 出现必须响应的确认卡片时，可以显式提示，但不强制滚动覆盖用户位置。

## 错误与中断

- 单个工具失败：run 可继续，摘要累计失败数，详情标记对应条目。
- run 因错误结束：状态为 `failed`，保留后端错误提示和可展开记录。
- 用户停止任务：状态为 `interrupted`，摘要显示“已停止”及已执行操作数。
- 进程异常结束且工具结果缺失：沿用后端悬挂调用修复结果，展示为失败项。
- 缺失或无法解析的参数/结果：详情使用安全字符串化和长度限制，摘要仍可展示。

## 无障碍与视觉约束

- 摘要使用真实按钮，提供 `aria-expanded` 和关联详情区域。
- 运行状态除动画外必须有文本；成功和失败不能只依赖颜色表达。
- 尊重 `prefers-reduced-motion`，关闭旋转或脉冲动画。
- 摘要保持单行省略，窄屏优先保留状态和失败数，隐藏当前动作次要文本。
- 详情中的长命令与输出继续限制高度并允许内部滚动。

## 测试策略

### 纯函数测试

- 20 个连续 Bash 调用生成一个 activity，操作数为 20。
- call、progress、result 按 `toolCallId` 合并且状态正确。
- 思考片段不计入操作数，但能出现在展开详情中。
- 成功、失败、中断和悬挂调用产生正确的摘要状态。
- 持久化消息与等价实时消息生成相同展示模型。

### 组件测试

- 运行中和完成后均默认只显示单行摘要。
- 点击摘要展开、再次点击收起，并正确设置无障碍属性。
- 新事件更新已存在的活动区，不创建新的活动组件。
- 失败摘要和失败详情可见；确认卡片不会被聚合隐藏。
- 窄屏下摘要不会撑破消息区域。

### 集成与回归测试

- 模拟多轮 assistant message 与工具调用，确认最终回答独立展示。
- 刷新页面后，历史记录仍默认折叠且详情完整。
- 活动摘要频繁更新时，用户向上滚动的位置保持不变。
- 现有产物卡片、知识库调用、停止按钮和 run 耗时不受影响。

## 实施顺序

1. 为活动投影补充纯函数及测试。
2. 提取 `AgentActivity.vue`，迁移过程详情模板和样式。
3. 在 `ChatPanel.vue` 接入活动组件和新的滚动触发条件。
4. 补充实时、历史、失败和移动端测试。
5. 观察长任务场景；若确定性标签不足，再评估服务端阶段事件。

## 验收标准

- 连续执行 20 次工具调用时，默认视图始终只有一个活动摘要区。
- 活动摘要能显示状态、耗时、操作数量和当前动作或失败数量。
- 完整工具参数与结果最多一次点击即可查看。
- 最终回答不被过程记录分割，完成后过程默认折叠。
- 工具失败、任务中断、确认请求和刷新历史均不会丢失关键信息。
- 不变更共享事件协议、数据库结构或已有历史数据。
