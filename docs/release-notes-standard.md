# 版本更新说明规范

## 目的

每次创建 GitHub Release 时，应将当前版本相对于上一个版本的用户可见变更整理为简洁的更新内容。更新内容使用 `1、2、3` 这样的编号列表，避免直接展示单条 Git commit 信息。

## 适用范围

- 适用于所有版本发布，尤其是大版本和包含多个功能变更的版本。
- 更新范围为上一个版本 tag 到当前版本 tag 之间的全部提交。
- GitHub Release 的“更新内容”和桌面端自动更新使用的 `latest.json` 中的 `notes` 应保持内容一致。

## 整理步骤

### 1. 确定版本范围

确认上一个版本 tag 和当前版本 tag，然后查看版本范围内的提交：

```bash
git log --pretty=format:"%h %s" <上一个版本 tag>..<当前版本 tag>
```

例如：

```bash
git log --pretty=format:"%h %s" v1.3.18..v1.4.0
```

### 2. 筛选用户可见变更

优先保留会影响用户使用体验的提交，并按实际效果合并重复内容：

| 提交类型 | 整理规则 |
| --- | --- |
| `feat` | 通常纳入更新内容，说明新增能力和用户价值 |
| `fix` | 纳入面向用户的缺陷修复 |
| `perf` | 纳入用户能感知的性能或响应速度优化 |
| `refactor` | 仅在行为或体验发生变化时纳入 |
| `docs`、`test`、`chore`、`ci` | 默认不纳入；只有直接影响发布或用户使用时才说明 |
| `revert` | 根据最终生效的变更整理，不直接照搬提交标题 |

### 3. 转换为更新条目

每条内容应使用“动作 + 变更对象 + 用户收益”的表达方式：

- 使用中文动宾短语，简洁说明做了什么。
- 不展示 commit hash、内部文件路径、开发者姓名或协作者信息。
- 避免直接复制技术实现细节；必要时只保留对用户有帮助的技术说明。
- 按“重要功能 → 体验优化 → 问题修复”的顺序排列。
- 合并同一功能下的多个提交，避免一个功能拆成多条重复描述。

## Release 内容格式

推荐使用以下结构。更新条目数量以实际变更为准，不为了凑数强行补充；通常保留 3～8 条：

```markdown
## 更新内容

1. 新增 <功能名称>，支持 <用户可执行的操作>。
2. 优化 <功能或流程>，提升 <用户收益>。
3. 修复 <用户可见问题>，避免 <问题影响>。

## 下载说明

- macOS 手动安装请下载 `.dmg` 文件。
- `.app.tar.gz` 是应用自动更新专用文件，请勿手动下载解压安装。
- 未配置 Apple Developer 公证时，首次启动请右键应用并选择“打开”。
```

下载说明与更新内容分开维护，不要把安装包、签名文件或 CI 构建细节混入编号列表。

## 自动发布注意事项

`${{ github.event.head_commit.message }}` 只代表触发工作流的最后一次提交，不能直接作为完整的版本更新说明。自动发布流程应使用按照本规范审核后的编号列表，并将同一份内容同时用于：

- GitHub Release 正文的“更新内容”。
- `latest.json` 的 `notes` 字段。

如果发布流程无法自动生成经过整理的内容，应在创建 Release 前手动补充和审核编号列表。

## 示例

以 `v1.4.0` 为例，Release 内容可以整理为：

```markdown
## 更新内容

1. 新增会话 Token 输入、输出及累计用量展示。
2. 优化文件交付卡片校验，避免将未实际生成的文件显示为可下载卡片。
3. 完善桌面端发布版本校验，统一 npm、Tauri 与 Cargo 版本号。
```

## 发布前检查

- [ ] 已基于上一个版本 tag 到当前版本 tag 的提交进行整理。
- [ ] 每条内容都是用户可理解的变更，而不是原始 commit 标题堆叠。
- [ ] 更新内容使用 `1、2、3` 编号列表，并已合并重复项。
- [ ] Release 正文与 `latest.json.notes` 使用同一份更新内容。
- [ ] 下载说明仍保留在更新内容之后。
- [ ] 已核对编号列表与实际代码变更一致，没有夸大或遗漏用户可见影响。
